# story-watch

This repo is developed in WSL and deployed to an unprivileged Debian 12 LXC (CT 120) on a Proxmox host that is reachable over Tailscale. Claude Code as a development tool runs only on the workstation. With `CLASSIFIER=claude` it is also installed in the CT as the tagger (#41): a pinned binary, run headless by the watcher with no tools, no MCP and no settings; it is never used interactively there.

- Tests: `.venv/bin/pytest`. Tests must never touch the network; mock instaloader and HTTP.
- Deploy: `PVE_HOST=root@<proxmox> CTID=120 ./deploy/push.sh`. It runs `deploy/install.sh` inside the CT, and that script must stay idempotent.
- Remote logs: `ssh root@<proxmox> pct exec 120 -- journalctl -u story-watch -n 100 --no-pager` (`-u story-watch-bot` for the bot; `| grep tagger` shows each story's `claude tagged … in N s` or its fallback). Proxmox SSH goes through Tailscale SSH in check mode, which can hang forever on an auth URL: probe with `timeout 15 ssh -o BatchMode=yes root@<proxmox> true` first.
- Production runs `CLASSIFIER=claude` (deployed 2026-10-11). Code defaults (`rules`) are for tests and fresh installs only.
- Target is Python 3.11 (Debian 12). Don't use newer syntax or stdlib features.
- Never log or put the Discord webhook URL or the session contents in exception messages. requests exceptions include the URL, so log only their type.
- An item is marked seen only after `DISCORD_WEBHOOK` returns 2xx, or when every post type it could have is filtered out by `NOTIFY_*`, or when a rule of the server-wide no-post list (`/nopost`, `story_watch/nopost.py`) drops it (both recorded with `notified_at` NULL).
- Instagram errors back off exponentially (cap 3600 s). Session or checkpoint errors send one alert and do not crash the service.

## Instagram

- `web_profile_info` (`Profile.from_username`) returns 429 for this account. Targets carry their userid in `TARGETS` (`name:userid`), so the lookup is skipped.
- Don't call `Story.get_items()`. It also requests the iPhone `reels_media` endpoint, which returns an empty reel for this session and raises `KeyError`. Read `story._node["items"]` instead.
- The GraphQL feed has no stickers. Link stickers (`story_link_stickers`) and @mentions (`story_bloks_stickers`) come only from the JSON embedded in the `/stories/<user>/` HTML page. Fetch that page only when a cycle has new items. A failed page fetch drops links and mentions, but must never block a notification.
- Never mark stories seen on Instagram. Plain HTML fetches run no JavaScript, so they don't. Don't add requests to `xdt_mark_story_reel_seen` or similar endpoints.

## Job pages and classification

- Job-page fetches (`story_watch/jobs.py`) go to arbitrary sites from inside the home network. They must never carry Instagram cookies, must be https-only, must check for a public address on every redirect hop, must connect to the address that was checked (`SafeFetcher` pins it; SNI and certificate checks stay on the hostname), and must stay size-capped. Each link's lookup is capped at `LOOKUP_BUDGET` (30 s wall clock) and never raises, and the HTML scans and the tagger rules stay linear-time (pages are attacker-controlled). Keep these guards. The tagger's still download (`hybrid.CdnImages`) uses the same ones.
- Classifiers implement `classify(item) -> Tags` (`story_watch/tags.py`, contract in `docs/tags.md`) and are registered in `CLASSIFIERS` in `story_watch/classify.py` (factories get the `Config`). Each dimension is the set of values the classifier can't rule out; an empty set is invalid and doubt is expressed by widening the set. `rules` (the default) is a placeholder: any link means post type `{job_posting}`, everything else `{misc}`, and all other dimensions are left unsure. It must not guess `process_info`, because keyword rules only produced false positives. If a classifier raises, the watcher uses `Tags.unsure()` (fail open: the story is still posted and pings every user who could match). Tags are stored per media id at first classification and reused on retries. `NOTIFY_*` acts on the post type only; `*_INTERVIEW_INFO` are deprecated aliases of `*_PROCESS_INFO`.
- `hybrid` (`story_watch/hybrid.py`) is #10's tagger, kept as the alternative to `claude` but not used in production: Qwen3-VL-4B through the local `story-watch-llm` unit decides post type and role; rules (`tag_rules.py`, `posting_rules.py`, `companies.py`) decide company, sponsorship and level. Its configuration is frozen with #10's scores: changing the model, prompt (`story_watch/prompts/`), request or rules means re-scoring with `scripts/eval_tagger.py --tagger hybrid` first, and bumping `RULES_VERSION`. The company lists live in `companies.py`; `docs/tags.md` shows them and `tests/test_companies.py` keeps the two equal. With `hybrid`, story data never leaves the host (`LLM_URL` must be local). `install.sh` installs `story-watch-llm` only with `CLASSIFIER=hybrid` and stops it otherwise. Since #45 `/opt/story-watch` is 0750, so the `storywatch-llm` user can't reach `llama.cpp/` and `models/` there; move them out (e.g. `/opt/story-watch-llm`) before bringing hybrid back.
- `claude` (`story_watch/claude.py`, #41) is the production tagger the user chose on 2026-10-10: Claude Opus via headless `claude -p` on the owner's plan (`CLAUDE_CODE_OAUTH_TOKEN`) decides all five dimensions from the still and the full listing text; the only post-processing is the Canada safety net, which may only widen sponsorship. Its prompt and schema (`prompts/tag_claude_v1.*`) are frozen with the bake-off's scores (0 missed / 11 extra / 2 ruling out); a test pins the prompt's hash. Changing the prompt, schema, company lists or post-processing means re-scoring with `scripts/eval_tagger.py --tagger claude` first and bumping `CLAUDE_VERSION`. Never make live `claude -p` calls from tests; the usage is the owner's (one Pro plan shared with the owner's own Claude use, about 0.17% of a five-hour window per story). The CLI in the CT is pinned in `install.sh` (`CLAUDE_CLI_VERSION` + `CLAUDE_CLI_SHA256`, installed under `/opt/story-watch/claude/<version>`); to bump it, update both, check that the stream-json `rate_limit_event`/result format is unchanged (an unknown status counts as a limit, so a format change sends every story to the fallback), and watch `grep tagger` after the deploy.
- The Claude call stays sandboxed: `--tools ''`, `--strict-mcp-config`, `--setting-sources ''`, `--safe-mode`, `--no-session-persistence`, a private 0700 HOME under the state dir, an empty cwd, a minimal env. The token goes only in the subprocess env, never argv, logs or exception messages (the `DISCORD_BOT_TOKEN` rule). Listing and image text are attacker-controlled: keep them delimited, keep validating the reply strictly against the schema (anything else is a failure), and never let the reply do anything but pick tag values. Any failure (usage limit, timeout, non-zero exit, bad output) gives the fallback (`listing_rules` with OCR text); `CLAUDE_TIMEOUT` (60 s) kills the process group, a cycle waits on Claude at most 300 s, and Claude is alerted on once per outage.
- The hybrid never blocks a post: any model failure, a timeout (`LLM_TIMEOUT`, 90 s) or a missing still gives the fallback tags (`listing_rules`, with the OCR text). After a timeout or refused connection the model is skipped for the rest of the cycle, and a cycle waits on it at most `CYCLE_BUDGET` (600 s). The watcher calls `start_cycle()` (a `/health` check) before every cycle and alerts once after `TAGGER_ALERT_AFTER` (15 min) down, then "recovered". Never log the prompt, posting text, OCR text or the model's reply.
- The project supports exactly one Discord server (decided 2026-10-08). Stories, deploy messages, alerts, heartbeat and `--test-notify` all go to `DISCORD_WEBHOOK`. Leftover `DISCORD_WEBHOOK_<n>` / `ROLE_<TYPE>_<n>`, and the removed role pings (`PING_ROLES`, `ROLE_<TYPE>`), only log a warning naming the variable. An old `deliveries` table may remain in existing databases; the code ignores it.
- The no-post list (#13, `docs/pings.md`) is one server-wide list of rules (a conjunction of tag dimension -> values each), stored in the state DB, edited with `/nopost` by `LABELER_USER_IDS` only and read by the watcher once per cycle (a read error means no list: fail open). It sits on top of `NOTIFY_*`. A story is dropped only when the tagger is confident on every dimension the rule uses (value set inside the rule's values and not "every value"; N/A never matches), a story with a job link or whose post type could be Job posting is always posted, and only a real model tagger's output can drop a story (`CLASSIFIER=claude` or `hybrid`, and not their fallback: `evidence` starting with `fallback:`; never `rules`); keep those guards (`nopost.matching_rule`) and their tests. Dropped stories keep `notified_at` NULL, log tag values only (never text or evidence), ping nobody and are still archived, so the label channel still shows them. The eval harness uses the same function to report dropped labeled job postings (must be 0).
- Discord pings are user mentions only: `<@id>` at the end of `content`, with `allowed_mentions` set to `{"parse": [], "users": [ids]}`. Never let Discord parse everyone or roles. The users are those whose `/pings` preferences (`Store.all_ping_prefs`, `should_ping`) match the story's stored tags. Fail open: if the preferences can't be read, post without pings and log the exception type only. Mentions that don't fit (100 ids or 2000 characters) go in best-effort follow-up messages, and the item counts as delivered once the main post returns 2xx. Alerts, the heartbeat, `--test-notify`, deploy messages and `NOTIFY_*`-filtered and no-post-dropped stories ping nobody. Only `scripts/resend_story.py` reads `TEST_PING_USER_IDS` and `TEST_DISCORD_WEBHOOK`, and it never reads real users' preferences. The service must never use them.

## Discord bot

- `story-watch-bot` (`story_watch/bot/`) is a gateway bot for one Discord server only. Labeling is its first feature; `/pings` (#16) and the "Fix tags" message context-menu command (#35) go in the same bot. Posting stories stays on webhooks.
- Fix tags (`bot/fix.py`, `discord_app.py`) is how the bot now writes labels from the main channel too. It works only while the story's rows exist (48 h, `Store.prune`). Corrections come only from stories someone disagreed with, so they are biased toward tagger errors: use them for error analysis, and keep the label channel for unbiased spot checks. The watcher posts with `?wait=true` and stores `message id -> media id` in `story_messages` (a failed id parse or store never fails a delivery). A fix (LABELER_USER_IDS only, through the same modal and a Save confirmation) appends a `source: "correction"` label, replaces the stored tags and edits the post's embed footer through the webhook (`Notifier.edit_message`: embeds only, `allowed_mentions` empty, so it never re-pings). The bot reads `DISCORD_WEBHOOK` only for that edit; same rule as everywhere, never log it.
- Two users (#45): the watcher runs as `storywatch` with `.env` (everything: `CLAUDE_CODE_OAUTH_TOKEN`, `IG_*`, the webhook); the bot runs as `storywatch-bot` with only `bot.env`, which `install.sh` derives from `.env` through the allowlist `BOT_ENV_KEYS` (`bot/config.py`, `bot/envfile.py`). The bot must never be able to read `.env`, `.config/instaloader` (the session) or `data/claude-home`. They share only `data/` (2770, setgid) and the archive (3770) through the group `storywatch-shared`, and both units use `UMask=0007` so SQLite's WAL files stay writable for both. A new bot setting goes in `BOT_ENV_KEYS` (a test checks the config reads nothing else); never widen the allowlist with watcher secrets.
- `DISCORD_BOT_TOKEN` follows the webhook rule: never log it, echo it or put it in exception messages; log exception types only. The unit must not restart fast or crash-loop (1000 IDENTIFYs per 24 h resets the token), and config or token errors exit 2 without a restart.
- Archive sidecars (`story_watch/archive.py`) also hold the extracted job posting (`posting`, description capped at 20,000 chars with `description_truncated`), taken from the posting already fetched for tagging; never fetch again for the archive. The eval harness prefers it over the saved listings dir. Old sidecars without the field must keep loading.
- Anything the bot writes goes at the top level of `ARCHIVE_DIR`, never in the per-target folders (`Archive.prune()` evicts `*/*`). Keep pure logic (`labels.py`, `queue.py`, `render.py`, `config.py`) free of discord imports. A person must confirm every label with Save.

## Workflow

- Iterate on embed, job and classifier output with `scripts/resend_story.py`. It caches stories in `story-cache/` and makes no Instagram requests unless given `--refresh`. Use `scripts/dump_story.py` to inspect raw Instagram JSON.
- When adding an env var, update `.env.example`, the README and `HUMANS.md` in the same change.
- `*.har` captures contain session cookies. Keep them gitignored, and delete them after use.
- A pre-commit hook (gitleaks + `.gitleaks.toml`, plus a filename block) scans every commit. Never bypass it with `--no-verify`; fake webhook URLs in tests must stay short (e.g. `/api/webhooks/1/secret`) so they don't match.
